1. Overview
Problem: Building ML models involves many separate tools: data cleaning, labeling, training, tuning, evaluation and serving. Stratal is a local, end-to-end ML lifecycle platform that runs on consumer hardware. It turns raw data into versioned datasets, trains and fine-tunes models, evaluates them, and serves them through a chat UI and an engineer dashboard.



Users:
End user: chats with models, generates images, translates text
AI engineer: manages data, builds and trains models, tunes, evaluates, monitors jobs


2. Phases
Phase	Scope	                                                 Done when
1	Data ops + image→text auto-labeling + eval	        10k raw images → captioned, filtered, versioned, split dataset with an eval report
2	Training runtime + model builder + classical ML + HPO	User builds a CNN in the UI, trains it on a dataset version, sees test metrics
3	LLM: caption refinement, RAG, router, tools	        Chat answers grounded in the corpus, with citations; router picks the correct model
4	Text→image LoRA fine-tune	                        LoRA trained on the phase-1 dataset; before/after samples + CLIP score
5	Translation + full chat UI + dashboard polish	        All 4 model types reachable from chat (manual + auto mode)

3. Functional Requirements
Module DATA: Data Operations

DATA-1 Ingestion

DATA-1.1 [P0][1] The system shall ingest all files from a source folder into stage 0 (raw), recording path, size, format and dimensions. — AC: 10k-file folder → stage0 manifest has 10k rows.
DATA-1.2 [P0][1] The system shall reject corrupt or unreadable files and record the reason. — AC: 5 planted corrupt files → 5 rows with status=rejected and a reason.
DATA-1.3 [P1][1] The system shall reject images below a configurable minimum size (default 256px). — AC: threshold can be changed via config; undersized images flagged.
DATA-1.4 [P1][2] The system shall ingest tabular (CSV/Parquet) and text (TXT/JSONL) sources. — AC: sample CSV and JSONL ingest without errors.

DATA-2 Cleaning & Deduplication

DATA-2.1 [P0][1] The system shall remove byte-identical duplicates. — AC: 20 planted exact copies removed.
DATA-2.2 [P0][1] The system shall remove near-duplicates using perceptual hashing with a configurable distance threshold. — AC: the same image saved at JPEG 90 and 70 → one kept.
DATA-2.3 [P2][1] The system shall detect semantic duplicates by clustering CLIP embeddings. — AC: cropped variants grouped together; report generated.
DATA-2.4 [P1][2] The system shall clean text: normalize whitespace and Unicode, and drop empty or over-length rows. — AC: planted bad rows removed and logged.

DATA-3 Versioning & Lineage

DATA-3.1 [P0][1] Each stage shall write a manifest (Parquet) containing per-row status and a content hash. — AC: every stage produces a manifest file.
DATA-3.2 [P0][1] Each dataset version shall get a version ID derived from its content hash and config hash. — AC: same input + config → same ID; any change → new ID.
DATA-3.3 [P0][1] The system shall record lineage (parent version, stage, config, timestamp) for each version. — AC: lineage can be followed from any version back to raw.
DATA-3.4 [P1][1] The system shall store versions as manifests pointing to files, not as full copies of the data. — AC: a new version adds only manifest bytes plus any new files.
DATA-3.5 [P2][2] The system shall show a diff between two versions (rows added/removed/changed). — AC: diff report lists the changes correctly.

Module RUN: Training Runtime
RUN-1.1 [P0][2] The system shall run training jobs from a queue with states (queued, running, paused, completed, failed, cancelled). — AC: state transitions logged; invalid transitions rejected.
RUN-1.2 [P0][2] The user shall be able to start, pause, resume and cancel jobs. — AC: each action works on a running job.
RUN-1.3 [P0][2] Jobs shall checkpoint every N steps/epochs and resume from the latest checkpoint. — AC: kill mid-training → resume continues from the checkpoint with matching metrics.
RUN-1.4 [P0][2] The VRAM manager shall keep at most one large model on the GPU and fully free memory on unload. — AC: torch.cuda.memory_allocated returns to baseline after unload.
RUN-1.5 [P0][2] The system shall detect OOM, catch it, mark the job failed with a clear reason, and suggest a smaller batch size. — AC: a deliberately oversized batch → clean failure, no crash.
RUN-1.6 [P1][2] The system shall monitor GPU temperature and pause jobs above a configurable limit, resuming when it cools. — AC: simulated high temperature → job pauses then resumes.
RUN-1.7 [P1][2] The system shall detect hung jobs (no progress for T seconds) and mark them stalled. — AC: simulated hang → stalled status.
RUN-1.8 [P0][2] Jobs shall stream live metrics: loss, accuracy, step time, VRAM, RAM. — AC: dashboard updates live during a run.
RUN-1.9 [P1][2] The runtime shall choose CPU or GPU per job (auto or manual). — AC: tiny models default to the faster device, based on a benchmark.

REG-2 Weight Retention Policy
  Default rule: per model lineage, store ONLY
    (1) the ORIGINAL weights (base / pretrained model, or the
        initial weights of a from-scratch model), and
    (2) the MOST RECENT trained / fine-tuned weights.
  Everything in between is deleted unless the user opts to keep it.
 
  REG-2.1 [P0][2] The system shall always retain the original (base)
          weights of every model lineage. They can never be deleted by
          retention.
          -- AC: base weights still present after 10 training runs.
  REG-2.2 [P0][2] After a training / fine-tuning run completes, the
          system shall retain its weights as the new "latest" and
          delete the previous latest, unless it is kept by REG-2.3 or
          pinned (REG-2.5).
          -- AC: default config, 3 runs -> only base + run-3 weights
             on disk.
  REG-2.3 [P0][2] The user shall configure how many intermediate
          versions to keep: keep_intermediate = N (default 0 = keep
          none; "all" = keep every version). Retained = the N most
          recent versions before "latest".
          -- AC: N=2, 5 runs -> base + runs 3, 4 (intermediate) +
             run 5 (latest) on disk.
  REG-2.4 [P1][2] keep_intermediate shall be settable globally and
          overridable per model lineage.
          -- AC: global N=0, lineage X N=3 -> only X keeps
             intermediates.
  REG-2.5 [P1][2] The user shall be able to pin any version; pinned
          versions are exempt from retention until unpinned.
          -- AC: pinned run-2 survives N=0 cleanup.
  REG-2.6 [P0][2] In-run checkpoints (RUN-1.3) are temporary: during a
          run keep only the latest checkpoint (for resume); delete it
          when the run completes successfully. A paused/partial run
          keeps its checkpoint until it is resumed or cancelled.
          -- AC: completed run leaves no checkpoint files; paused run
             still resumable after cleanup.
  REG-2.7 [P0][2] When weights are deleted, metadata is kept: config,
          dataset version, metrics, lineage, and a "weights_deleted"
          status, so the version can be inspected or re-trained
          (reproducible via NFR-4).
          -- AC: deleted version still shows in registry with metrics
             and a "re-train" action.
  REG-2.8 [P0][2] Retention shall never delete weights that are:
          (a) in use by a running/queued job or loaded for inference,
          (b) the parent of an existing adapter/fine-tune (e.g. the
              base model a LoRA depends on).
          -- AC: attempt to prune an in-use or parent version is
             blocked and logged.
  REG-2.9 [P1][2] Retention runs automatically after each completed
          run and on demand; it logs every deletion (version, size
          freed) as a MON event, with a dry-run preview option.
          -- AC: dry-run lists what would be deleted; real run frees
             the reported bytes.
  REG-2.10 [P1][2] Changing keep_intermediate to a smaller N shall
           show a confirmation with the versions and disk space
           affected before deleting.
           -- AC: confirmation lists exact versions + MB/GB.
  REG-2.11 [P1][2] The registry UI shall show disk usage per lineage
           (base / latest / intermediate / pinned / checkpoints).
           -- AC: totals match actual bytes on disk.
 
  Config example (configs/retention.yaml):
    retention:
      keep_intermediate: 0        # 0 = only base + latest; "all" = keep every version
      overrides:
        sd15_lora_captions: 3     # keep 3 intermediates for this lineage
      delete_checkpoints_on_success: true
      dry_run: false

                        ├──► collector ──► SQLite/DuckDB (durable)

   tags samples with              └──► WebSocket/SSE ──► dashboard (live)
   active job_id + stage

The sampler runs as a separate process/thread from the jobs (this is what NFR-13 requires). It learns which job and stage is active from the event stream, so every resource sample can be tagged without the training loop knowing anything about monitoring.

Monitoring NFRs
NFR-11 Overhead: monitoring shall use < 2% CPU and add < 1% to job runtime. — AC: benchmark with monitoring on vs off.
NFR-12 Retention: per-second samples kept 7 days, then downsampled to 1-minute averages. — AC: retention job verified.
NFR-13 Independence: if the monitoring process crashes, jobs must not crash, and the reverse. — AC: kill the monitor mid-job → job continues.


 

4. Non-Functional Requirements
NFR-1 VRAM: peak usage < 5.5 GB for any local job. — AC: logged peak per job.
NFR-2 RAM: peak < 12 GB; datasets are streamed, never fully loaded. — AC: memory profile on a 20k-image run.
NFR-3 Throughput: captioning ≥ 2 img/s on the RTX 4050 (benchmark, then adjust the target). — AC: benchmark in README.
NFR-4 Reproducibility: same data + config + seed → same splits, same version IDs, and metrics within tolerance. — AC: two runs compared automatically.
NFR-5 Resilience: no job loses more than N minutes of work to a crash. — AC: kill tests in the test suite.
NFR-6 Latency: LLM first token < 2 s; RAG answer < 8 s on local hardware. — AC: measured on 20 queries.
NFR-7 Local-first: works fully offline after models are downloaded; remote is optional. — AC: phase 1–3 features run with the network disabled.
NFR-8 Security: no unsafe deserialization of untrusted files; model downloads only from configured sources. — AC: code review checklist.
NFR-9 Testability: every P0 requirement has at least one automated test named with its ID. — AC: test_<ID>_* exists for each P0.
NFR-10 Observability: structured logs (JSON) with job ID and version ID on every line. — AC: logs can be filtered by ID.
NFR-11 Monitoring overhead: < 2% CPU, < 1% added job runtime.
         -- AC: benchmark monitoring on vs off.
NFR-12 Telemetry retention: per-second samples kept 7 days, then
         downsampled to 1-minute averages.
         -- AC: retention job verified.
NFR-13 Independence: monitor crash must not crash jobs, and vice
         versa.
         -- AC: kill monitor mid-job -> job continues.
NFR-14 Storage: with default retention (keep_intermediate = 0), disk
         use per lineage <= base weights + latest weights + one
         in-progress checkpoint.
         -- AC: disk audit after 10 runs matches the bound.
NFR-15 Deletion safety: retention deletes are atomic per version
         (metadata updated only after files are removed; a crash
         mid-delete leaves a recoverable, consistent state).
         -- AC: kill during cleanup -> rerun completes without
            orphaned files or dangling registry rows.

           - Never initialize CUDA before a fork.

             support).

  HPO    : Optuna (TPE + MedianPruner); optuna-dashboard optional.
           Each trial = a job in the RUN queue.
  EVAL   : torchmetrics, sklearn.metrics, sacrebleu (BLEU/chrF),
           statsmodels (Wilson CI), pycocoevalcap (CIDEr — needs Java;
           else implement CIDEr-D yourself or demote to P2)

  LLM    : Ollama (llama.cpp) serving, LangChain + LangGraph,
           sentence-transformers, FAISS (faiss-cpu)

  IMG    : diffusers (SD 1.5), PEFT LoRA, accelerate, 8-bit Adam

7.7 Why Postgres + Redis + Celery

               queues, retries, Beat scheduling.

UI/UX workflow — DESIGN BEFORE CODE (mandatory gates)
  No UI page or component is implemented until its design is APPROVED
  by the human. Order:
 
  GATE 0  Design system  -> must be approved before ANY screen design.
  GATE 1  Screen inventory + user flows -> approved.
  GATE 2  Per-screen mockup -> approved (one screen at a time).
  GATE 3  Implementation -> visually matches approved mockup.
 
  Approval protocol:
  - After producing a design artifact, the agent STOPS and asks:
      "Screen <ID> ready for review: <link/path>. Approve, or list
       changes?"
  - Only an explicit "approved" from the human passes the gate.
    Silence, "looks ok-ish", or partial feedback = NOT approved.
  - Each revision is versioned (v1, v2...) and its changes listed.
  - Approved mockups are stored in docs/design/screens/<ID>_vN.(html|png)
    and logged in docs/design/APPROVALS.md:
      <date> | <screen ID> | vN | approved by | notes
  - If implementation needs to deviate from an approved mockup, the
    agent asks first; it never silently diverges.

GATE 0 — Design system (docs/design-system.md + code tokens)
  The agent writes the design system FIRST, covering:
 
  a) Principles
     - Information-dense but calm: an engineering tool, not a marketing
       site. Data first, chrome second.
     - Status must be readable at a glance (running/paused/failed).
     - Avoid generic template look: distinct type pairing, deliberate
       color, consistent iconography.
     - Every screen has defined empty, loading, error, success states.
 
  b) Tokens (defined once; exposed as CSS variables + Tailwind theme)
     - Color: neutral scale (bg, surface, border, text-primary/
       secondary/muted), brand/accent, semantic (success, warning,
       danger, info), job-state colors (queued, running, paused,
       completed, failed, cancelled, stalled).
     - Data-viz palette: categorical (8 colors), sequential, diverging;
       resource colors fixed app-wide (CPU, RAM, GPU, VRAM, temp).
     - Light + dark themes from the same tokens (dark is default for a
       monitoring tool; both must pass contrast).
     - Typography: UI font + monospace font (logs, IDs, metrics); type
       scale; tabular numerals for all live numbers.
     - Spacing scale (4px base), radii, borders, elevation/shadows,
       z-index layers.
     - Motion: durations/easings; respect prefers-reduced-motion.
     - Breakpoints: desktop-first (>=1280), usable at 1024.
 
  c) Components (each with variants + states: default, hover, focus,
     active, disabled, loading, error)
     Buttons, inputs, selects, toggles, sliders, tabs, tables (sortable,
     virtualized), cards, badges/status pills, progress bar with ETA,
     toasts, modals, drawers, tooltips, code/log viewer, metric tile,
     sparkline, live chart, timeline bar, lineage node, layer node
     (model builder), chat bubble, empty state, error state.
 
  d) Patterns
     Forms generated from JSON schema (UI-2.3) styling rules; live-
     updating numbers (no layout shift); long-running job feedback;
     destructive-action confirmation; keyboard shortcuts.
 
  e) Accessibility
     WCAG 2.1 AA contrast; full keyboard navigation; visible focus
     rings; never encode meaning by color alone (icons/text on status);
     aria-live for activity log and job status updates.
 
  f) Deliverables for approval
     - docs/design-system.md
     - docs/design/system-preview.html (all tokens + components rendered,
       light and dark)
     - tokens.css / tailwind theme file (implemented only AFTER approval)

Layout decisions to review

  1. List and detail side by side. Datasets on the left (248 px), the selected dataset's versions on the right. Selecting a dataset changes the URL to /datasets/:slug; the first dataset is selected on arrival.
  2. One row per version, newest first, with its stage, parent, row counts and the space it added. Total rows are not a column: every version of a dataset has the same number (INV-06), so it is stated once above the table. The counts are four numbers plus a small stacked bar, so the share of accepted rows reads at a glance. Lineage as a graph is SCR-03's job; here the parent column is enough.
  3. A running job that will create a version appears as a provisional first row, with its progress, until the version exists. You can see that work is under way for this dataset without leaving the list.
  4. One primary action, Ingest a folder, in the list's header: it is the way in for new data. Continue from this version is a row action (also on SCR-03), opening the same drawer with the version filled in.
  5. The drawer keeps the list visible behind it. Source is a choice of folder or version; the stages to run follow from it; each stage's settings are generated from its config schema, collapsed by default.
  6. Proposed, not yet in API.md: a GET /sources endpoint listing the folders under /sources, so the source field can offer them instead of asking you to type a path. Without it, the field is plain text and an unknown path is reported by POST /jobs as source_not_found.

Layout decisions to review

  1. Two columns: sessions (240 px) and the conversation. The conversation is one centred reading column of 760 px, so a line of an answer stays readable at 1280 px and at 1024 px alike; the space beside it stays empty rather than holding a side panel (open point 8c).
  2. The composer is fixed at the bottom, with the mode as a segmented control (LLM · RAG · Images, Alt+1–3) and, beside it, the one version the mode needs: the index in RAG, the labelled version in Images, nothing in LLM. Send becomes Stop while an answer streams.
  3. The person's message is a filled bubble on the right; an answer is an outlined bubble on the left, with everything about it inside its border: the text, then the sources (RAG), then the footer. An abstention's border is dashed; a refused or failed answer has the dark error border.
  4. Citations are small boxed numbers in the text, links that scroll to their source under the answer and, with a second click, open SCR-03 on the chunk. The sources list puts the cited ones first, each on one line: number, document › section, the chunk's first words, relevance; the sources given but not cited are folded into "3 more sources given" with dashed numbers.
  5. The footer is always shown, one line of small mono text: route, model and revision, device, cold start when there was one, time to the first token, total time, tokens per second, and the index version for RAG. NFR-6 is then read on screen for every answer.
  6. Images are a 5 × 2 grid inside the answer bubble, 112 px thumbnails with the similarity and the file name under each; one opens SCR-03 on its row.
  7. The GPU line sits above the composer only when it matters (a job holds the GPU, or the model is loading), says which job and what still works, and links to SCR-04. A gpu_busy refusal then appears in the answer's place with Retry, the person's message kept.
  8. Sessions are listed newest first, titled by the first question, with the last mode and the time; New chat at the top. At 1024 px the list folds to a 48 px rail with New chat and a button that opens it over the conversation.

2How are dataset version IDs computed?
3
A version ID is ds_ followed by the first twelve hex characters of a SHA-256 over two hashes: the content hash of the rows and the hash of the config 1. Each row is encoded with its non-null columns in name order and hashed, and the row digests are added together, so row order and file compression do not change the ID 1. Because versions are immutable and stages exchange version IDs, the same parent and config reuse the existing version 2.

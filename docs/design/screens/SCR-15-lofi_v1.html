Layout decisions to review

  1. Two columns under one header. The operations on the left (400 px), the result on the right: the resulting schema as chips, then the preview table. Editing on the left and reading on the right stay on screen together; nothing scrolls the page at 1280 × 800 except the operations list itself when it is long.
  2. Run sits in the page header, on the right, with its two choices before it as radio buttons, Through clean and split (default) and Transform only (open point 6a). Reset is a ghost button beside it. While there are problems, Run is disabled and the count beside it reads "2 problems", each a link to its card.
  3. An operation is a compact card: its number, the op as a select, a ⋮ menu (Move up, Move down, Duplicate, Remove) and a drag grip; its fields on one line under it, generated from the schema; under them one grey line saying what it did on the sample. A refused operation gets a dark border and its message under the field the error's loc names.
  4. Column fields are selects of the columns at that step (open point 6c: the preview's steps), so after the rename, step 4 offers od280_od315, not the old name. drop takes several columns as chips; reorder opens the full list with up and down buttons.
  5. Add operation is a menu at the end of the list, one line per type with what it does, and a note at its foot that scaling, imputation and target encoding are the model's (DATA-7.1.AC2). The P2 types derive and filter are listed only once built (SCREENS §1: unbuilt is hidden).
  6. The resulting schema is a line of chips, one per column in order: name, kind, encoding when not the default, target marked. Changed columns are outlined, a dropped one struck through where it was. It answers "what will the model see" before reading rows.
  7. The preview is a dense table: row key pinned on the left, then status and reason, then the resulting columns in order; the table scrolls sideways under the pinned key. Cells an operation changed are bold; a new or recast column's header says so under its name. Above it: "First 50 rows of 178 · 50 accepted", plainly the sample's counts.
  8. Later stages, folded under the operations list, holds the clean and split settings (generated from their schemas, as in the Start pipeline drawer). It is greyed when Transform only is chosen.

One question this layout depends on

  1. Which rows does the preview show? Rule 32 says the first 50, and the AC1 test compares them with the stage's first rows. The wine CSV is sorted by cultivar, so its first 50 rows are all class_0: a set_target or a filter on the class would look odd in the preview. I propose keeping the first 50, as approved: simple, the same rows on every edit, and the header says "first 50 rows". The alternative is 50 rows spread evenly through the table (every 178 / 50th row), still fixed and still testable by row key, but a change to rule 32.

Layout and hierarchy only. Everything the approved SCR-09 already has (model, data, training form, start from, device, the VRAM check) keeps its approved design; this wireframe draws only what M10 adds. Blue numbers are annotations. There are two set-ups. The first tunes the Small CNN on CIFAR-10 (ds_f8e67211dd94). The second tunes a random forest on breast cancer (ds_2b7e04a91c55, 455 / 57 / 57 rows, 30 numeric columns, target diagnosis).

Layout decisions to review

  1. The study part is the collapsed section Tune with a study, as approved. Opening it turns this run into a study: the primary button becomes Start study, and the right-hand column explains what a study will do. Closing it again leaves an ordinary run, and the markers are kept until you leave the page.
  2. Any field can be marked tunable in place. While the study section is open, each field of the generated form gets a tune toggle. Turned on, the field's input becomes a range: low and high with a linear or log scale (and a step for whole numbers); choices as chips for an enum; both values for a yes/no field. The defaults come from the field's own range in its schema, and a range can never go outside it (HPO-1.1).
  3. Model parameters too. Add a model parameter lists the spec's tunable node fields (for example c1.out_channels or d1.p) and the estimator's own parameters, with the same range controls. The spec stays as built on SCR-08; a study only varies the fields you pick.
  4. The search space is listed in the study card, one row per marker, with its type and range in words ("learning_rate · log · 1e-4 to 1e-1"). A marker the server refuses (422) shows its reason on its own row (frame C).
  5. Limits, objective and pruning sit next to the space. Trials (default 20) and a time budget (default 1 h), with "whichever comes first" written out. The objective is chosen from the task's validation metrics, with its direction shown. Pruning is on by default and its rule is written in words. For a classical model, cross-validation folds (default 5) are shown in place of epochs.
  6. The VRAM check takes the worst case in the space: the largest batch and the widest layers. It still warns rather than blocks. A trial whose own settings would go over the cap is not run and is recorded as failed · over_vram (ADR-0018 rule 2), and the column says so.
  7. Choosing a classical model happens on this page (ADR-0019 rule 15). The model card gets two modes: Network (from SCR-08, as today) and Classical, with an estimator picker filtered by the dataset's task and a parameter form generated from GET /ml/estimators/schema (UI-2.3). A cross-field rule shows on its field before anything is sent (ML-1.4). A classical model has no device choice (it runs on the CPU) and no VRAM check. This adds ML-1.1 and ML-1.4 to SCR-09's inventory entry; SCREENS.md is updated if you approve. The alternative is a separate picker screen, which the inventory doesn't have.
  8. The data card states the task that the dataset's target implies (classification or regression, ADR-0019 rule 2). For text it also gives the vocabulary size and L from the tokenized version (rule 9).
  9. Start study opens SCR-10 for the new study, not SCR-04. The first trial's live view is one click from there.

Folds are drawn from the train split, grouped so duplicates never sit on both sides (ADR-0018 rule 4). The validation split scores the best configuration once it is refit; it is not used for tuning.

Where it runs

On the CPU queue, all trials in one job (a trial here takes seconds). Up to 50 trials or 10 min. The best configuration is refit on the train split, scored on validation, registered, then tested once.
No device choice and no VRAM check for classical models.
Start study →

With the study section closed, the same card trains one random forest with the values set (ML-1.1), and the primary button is Start run. The estimator list depends on the task: for regression it offers linear, ridge and lasso, and for any table the unsupervised kmeans, dbscan, hdbscan and pca, which ignore the target.

Layout decisions to review

  1. One page, one card per section, with an index on the left. There are four short sections; one scrolling page keeps everything findable with Ctrl+F. The index marks a section with unsaved changes with a dot.
  2. Each section saves on its own. A Save and Discard bar appears under a section only when it has changes, with how many fields changed. Leaving the page with unsaved changes asks first. A retention change waiting on its confirmation never holds up a training change.
  3. Every field comes from the API's JSON schema (UI-2.3): label, unit, help, default, minimum and maximum. A changed value shows changed and a reset to default link. The page has no field list of its own, so a new setting needs no UI change (UI-2.3.AC1).
  4. Each field says when it takes effect. The temperature limits and the stall timeout apply to running jobs at once, since the watchdog reads them on every check. The checkpoint interval applies to jobs started after the save, because a job's config is fixed when it starts (NFR-4).
  5. The thermal fields show the live context: the GPU's temperature now, the highest in the last 7 days and which job reached it, and the card's own slowdown point read from NVML. The pause limit's maximum is that slowdown point; resume must be at least 5 °C below pause. The 87 °C drawn here is an example; the real value is read from this card.
  6. The ranges are proposals for you to accept: checkpoint interval 1–60 min, pause 60 °C to the slowdown point, a 5 °C gap between pause and resume, stall timeout 60–3600 s, N from 0 to 100 or all. SPEC gives only the defaults (OC-3).
  7. Retention has a global default and a table of per-lineage overrides (REG-2.4). N is a number or all. Lowering N, globally or for one lineage, first runs the dry run and opens the confirmation with the exact versions and sizes (REG-2.10), as on SCR-11. Lineages that have an override are listed as not affected by a global change.
  8. Two values in SPEC's retention.yaml example are not settings. delete_checkpoints_on_success is shown as a fixed rule, because REG-2.6 requires it. dry_run is an action (Preview cleanup on SCR-11 and the confirmation here), not a stored value.
  9. Theme stays in the browser. The design system stores it per browser and follows the system on first visit, so the Appearance card says so and writes nothing to the database.

The list is the dry run's result; if anything changes before the confirmation, it is refused and a new list is shown (ADR-0015 rule 7). "Keep them" has the focus. A global change spans lineages, so there is no single name to type; the phrase names the count instead. Confirming saves the setting and starts the retention job, which SCR-11 and the jobs list then show. Raising N, or a change that deletes nothing, saves without this dialog.

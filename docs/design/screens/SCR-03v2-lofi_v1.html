Layout decisions to review

  1. Three new tabs beside Rows, Reasons and Config: Distributions (UI-2.2), Compare (DATA-3.5) and, on a version models train on, Models (UI-2.1). The tiles, lineage strip and Rows stay as approved. The Reasons tab already lists every reason with its stage, so it is unchanged.
  2. Distributions opens with the funnel: one row per stage from raw to this version, with rows in, what the stage removed (by reason, as chips that filter Rows) and rows out. A split adds its three parts. This is "rejection reasons per stage" read top to bottom.
  3. Then the columns, raw against here. Raw is the lineage's ingest version, every row; here is this version's accepted rows. Each column gets an overlaid histogram (raw as an outline, here filled) and a five-number table (min, p10, median, p90, max) for both. A third row, removed, summarises the rows the pipeline dropped, which is usually what explains a difference (the 60 rejected images all have a shorter side of 120–255 px).
  4. Which columns, by type: labelled images: width, height, file size, the preprocessed long side, caption length and CLIP score once labelled; labelled images (CIFAR): class counts per split; texts: length in words and, on a tokenize version, tokens and the share cut at L; tables: rows and the target's distribution (the column view is M11b's).
  5. Compare picks another version of the same dataset (a select, newest first, the parent preselected). It shows the config difference first, since that is usually the cause, then rows added, removed and changed, the changed count by field, and the changed rows with each field before → after; a row opens its drawer on either side.
  6. The diff matches rows by row_key (K10) and compares the fields both versions have; a field one side lacks (a label version's caption against a clean version) is listed once as "only in B", not per row.
  7. Semantic clusters look like duplicate groups (ADR-0013 rule 5): a tile on a label or later version ("105 clusters · 290 rows"), a Rows filter In a semantic cluster, a cluster chip in the row, and in the row drawer the cluster's members side by side with each pair's similarity and "kept in one split group". Unlike a duplicate group, every member is accepted, so none is marked kept.
  8. Models lists the model versions trained on this version, grouped by lineage: state, main metric (test if scored, else validation, said which), weights, trained, with links to SCR-11 and Compare on this test split (SCR-11 v2). The lineage strip gains a "→ 16 models" end chip that opens the tab.

Two questions this layout depends on

  1. Should a change to a row's reason text alone count as "changed"? In the real diff of frame B, 60 rows differ, but 59 of them only in reason_detail ("below the minimum 256px" → "255px"): one image really changed (rejected → accepted). I propose counting a row as changed when its status, reason code, content or derived fields differ, and listing wording-only changes on their own line ("59 rows: reason wording only"). Otherwise the headline would read 60 changed rows for a one-row change.
  2. Can Compare cross stages? Within a dataset every version has the same rows (INV-06), so a clean version can be diffed against a split; the split's own columns would show as "only in B". I propose allowing any two versions of one dataset and saying when the stages differ. The alternative is to offer only versions of the same stage.

Layout and hierarchy only. Blue numbers are annotations. The tab was named in SCR-13's approved mockups and is hidden in the build until it passes its gates. The data is real, from the dev database: frame A is every run of train on the GPU in one group, frame B every run of label, frame C the last 20 GPU training runs. Times are local. The header, side navigation and the other two tabs are SCR-13 as built.

Layout decisions to review

  1. One stage at a time. A Stage select lists every stage that has completed runs, newest first, with its queue and count (train · GPU · 30 runs). A rate or a peak only compares within one kind of work: images a second for label and samples a second for train share no axis.
  2. Like with like. Within a stage, runs are grouped by what ran: for training, the model lineage and the batch size (small_cnn · cifar10 · batch 128); for a pipeline stage, its model and batch, or its config. The default group is the latest run's, since the question is usually "is this run like the ones before it?". All groups (frame C) puts every run against its own group's median, so different models share one axis.
  3. The last N runs, not a time range. N is 10, 20 (the default), 50 or 100, and is a maximum: a group with fewer runs shows them all and says so. The header's range presets are hidden on this tab, which counts runs, not hours. Runs are evenly spaced, oldest on the left, with the days marked under the axis.
  4. Honest numbers.
    • Rate counts work done, not work reused, in the stage's own unit: samples a second for training (its moving average while training, the one its ETA uses, times the batch); captions computed a second for label; files for ingest; images for clean and preprocess. A run that reused everything has no rate and is drawn hollow (frame B).
    • Time is running time across attempts, with pauses and queueing removed, as Compare two jobs aligns runs. For training it is shown per epoch, since runs have 3, 10 or 30 epochs. A resumed run therefore shows what it really cost.
    • Peaks are the stage's MON-2.5 peaks: the card's VRAM, PyTorch's allocated memory, the VM's RAM and the temperature. The job's RSS stays in the table only: it counts the loader workers' shared memory once per worker (7.4 GB against a 3.25 GB container limit).
  5. Each lane draws the group's median as a dashed line with its value, and the thresholds where they exist: NFR-1's 5.5 GB, RAM 85 %, the 83 °C pause and the 75 °C resume. A run that paused, resumed after a lost worker, was pruned or was a fine-tune carries a short tag, so an outlier explains itself.
  6. The table under the lanes is their text equivalent (accessibility), newest first and sortable by any column. A point or a row opens the job on SCR-04. Two ticked rows give Compare these two, which opens Compare two jobs with A and B.
  7. Live: when a run of the chosen stage completes, it joins on the right through the existing global stream; once N is reached, the oldest leaves on the left. Nothing else moves.

Three questions this layout depends on

  1. One stage at a time, or one row per job with all its stages? I propose one stage at a time. One row per job answers "what did each job cost", but it cannot draw a trend, because its columns measure different things for different jobs.
  2. The default group: the latest run's configuration, or All groups? I propose the latest run's. All groups stays one click away, and relative values are harder to read first thing.
  3. N = 20 by default? Twenty points stay readable at 1024 px; 50 and 100 are for looking further back.

Layout decisions to review

  1. Comparison is its own page under Models, /models/compare, because K8 compares across lineages and a lineage's page shows one. The URL holds the split and the versions, so a comparison can be bookmarked. It is reached from Compare… on the registry list and from Compare on this test split in a version's drawer, which opens it with that version already chosen.
  2. One test split per comparison. The header names it: dataset, split version, test rows, task and classes. The picker lists only versions tested on that split, grouped by lineage, newest first; 2 to 6 can be chosen (EVAL-1.3 asks for 3 or more; 6 keep the columns readable at 1280 px). Versions whose weights were deleted stay comparable: their metrics are kept (REG-2.7).
  3. Versions are columns, metrics are rows. The task's EVAL-1.2 set (classification: accuracy, macro F1; regression: MSE, MAE, R²), then facts: lineage, kind (network or classical), parameters, epochs, trained, parent. The best figure in each row is in bold and marked "best" in words, never by shade alone.
  4. Uncertainty is shown, not hidden (K8). Accuracy carries its Wilson 95 % interval in the table and as a dot-and-whisker chart. When the intervals overlap, one sentence says the split cannot tell the models apart. Here, 18 test rows give 0.74–0.99 for 17 of 18 and 0.82–1.00 for 18 of 18.
  5. Per-class F1 side by side, classes as rows and versions as columns, each cell with its figure and a small bar. Sorted by the largest spread between versions, so the classes where the models differ come first. Above 20 classes it shows the 20 with the largest spread and says so. A version's confusion matrix opens in its drawer (SCR-11's task metrics).
  6. Try it follows the version's input. The image form is unchanged. A table gets one field per feature from the table schema, numbers or a category list, with the target left out; an empty field is sent as null and imputed, as the API already allows. A text gets a text box. Each has Fill from a test row, which also shows that row's true label next to the prediction.
  7. Answers by task: classes as up to five bars with probabilities; a value with the target's name; a cluster ID; a PCA projection as its components. Below, the served line as today ("Served on the GPU · cold start 11.3 s · 13.0 s"). A refused record marks each field the API names (wrong_input, loc: body.record.<name>).
  8. The parent across lineages. The version drawer's Parent names the parent's lineage when it is another one and links to it. A new Fine-tuned into row lists the versions started from this one. A lineage founded by a fine-tune says so under its title. Fine-tune… sits in the drawer's actions for a trained network version with its weights (→ SCR-09 v2, ?init_from=).

Two questions this layout depends on

  1. Versions trained before M10 have no test metrics. Test scoring arrived with EVAL-1.2, so on CIFAR-10's split ds_f8e67211dd94 only one of seven trained versions can be compared (the study's best, mv_a4a0fb846812, test accuracy 0.810). K8 said "no new evaluation jobs in M11". I propose one narrow exception: Score on test in the picker for a version that has weights and no test metrics. It queues the existing test_eval stage for that version, once. A version that already has test metrics is never scored again, so a study's "computed once" (HPO-1.4) still holds. Without it, they stay listed, greyed, with "no test metrics: trained before M10" (frame B shows both).
  2. Try it for texts could say how the text was read: its token count, how many words were unknown to the vocabulary, and whether it was cut at the maximum length L. The predict response has none of these today; adding input: {tokens, unknown, truncated_at} for texts is a small API change. I propose adding it (frame D draws it); without it the frame drops that line.
